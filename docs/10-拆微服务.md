# 拆微服务(阶段二伏笔兑现)

> 目标:ticket-server 单体按域拆成 user/train/ticket/order/pay 五个服务 + gateway。
> 核心命题:**把「方法调用」变成「远程调用」的代价是什么(分布式一致性),以及怎么最小化代价**。

## 1. 目标架构

```
用户 → gateway(路由 + JWT 验签)
        ├─ /api/user/**  → user-service(注册/登录/JWT 签发)
        ├─ /api/train/** → train-service(车次/车站查询)
        ├─ /api/ticket/**→ ticket-service(余票查询 + 库存扣减核心)
        ├─ /api/order/** → order-service(下单排队/建单/取消/对账 + MQ 消费者)
        └─ /api/pay/**   → pay-service(支付)
                ↓ Feign 内部调用
        order-service ──扣减/回补──→ ticket-service
        pay-service ────改状态────→ order-service
```

## 2. 拆分的核心问题(面试灵魂)

### 2.1 跨服务一致性:单库事务变成分布式补偿

单体里「订单 + sold 同步」在一个事务。拆开后:

- order-service 建单事务只包「订单 + 明细 + 凭证」
- 库存扣减/同步是**远程调用** ticket-service——跨服务无 ACID
- 失败顺序:deduct 成功 → 建单失败 → 调 refund 补偿(先扣后补,老思想新战场)

**面试金句:拆微服务 = 用分布式一致性(补偿/对账)换取独立部署与独立扩展——代价意识是拆分决策的前提。**

### 2.2 远程调用的幂等:拆分引入的新问题

Feign 超时重试 → deduct 被调两次 → 双扣!单体里不存在这个问题(本地调用不重试)。

解法:deduct 接口带幂等键(requestId),ticket-service 用 Redis SETNX 记录「已处理」——懒加载 SETNX 的老朋友第五次出场。

### 2.3 公共代码抽取:ticket-common 模块

Result/BizException/GlobalExceptionHandler/JwtUtil/雪花/IdentifierGenerator——五个服务都要用,抽成独立模块 `ticket-common`,各服务依赖它。**这是「代码不能跨服务复用」的正式解法。**

### 2.4 数据源与分片归属

- order-service:orders/order_item 的分片规则(它管订单)
- ticket-service:train_seat_stock 等库存表(主库,不分片)
- 其余服务:各自连主库
- 缓存归属:StockCache 在 ticket-service(读缓存 + 扣减缓存失效都在它内部,不再跨服务!)

## 3. 跨服务接口契约(Feign)

### ticket-service 暴露给 order-service(内部接口,不打给用户):

```
POST /api/inner/stock/deduct     body: {requestId, trainId, trainDate, seatTypeId, fromNo, toNo, count}
  → 幂等检查(SETNX requestId)→ 懒加载 → Lua 扣减 → DB sold 同步
  → 返回:成功 / 余票不足 / 已处理(幂等命中)

POST /api/inner/stock/refund     body: {requestId, 同上}
  → 回补 Redis + DB 回减(幂等)
```

### order-service 暴露给 pay-service:

```
POST /api/inner/order/payNotify  body: {payNo}
  → 订单 10→20 条件更新(原 handlePayNotify 的订单部分)
```

**注意内部接口的安全**:不打给用户的接口,网关路由不暴露 /api/inner/**;真实生产还要服务间认证(阶段二讲的「服务间认证」,现在条件成熟可以顺手做)。

## 4. 分步计划(每步验收)

| 步 | 内容 | 验收 |
|---|---|---|
| 1 | **ticket-common 模块**(Result/异常/JWT/雪花)+ parent pom | 原 ticket-server 依赖 common 后全测试绿 |
| 2 | **user-service 独立**(最独立,练手) | 注册/登录走 8081 网关路由到 user-service |
| 3 | **train-service 独立**(纯查询) | 车站/车次查询通 |
| 4 | **ticket-service 独立**(余票查询 + 扣减 API 化 + 幂等键) | 直连测试 deduct/refund 接口幂等 |
| 5 | **order-service 独立**(Feign 调 ticket;MQ 消费者迁入) | 下单全链路(排队→扣减→建单) |
| 6 | **pay-service 独立**(Feign 调 order) | 支付全链路 |
| 7 | 网关路由更新 + 全链路回归 | 九项业务验收全过 |

## 5. 为什么「先拆最独立的」

user-service 不依赖任何其他服务——拆它练熟流程(骨架/注册/路由/验收),再啃 order↔ticket 的硬骨头。**依赖最少的先拆,耦合最重的后拆,每一步都可验收。**

## 6. 面试自查

- 拆微服务的代价是什么?(分布式一致性、远程幂等、链路追踪、部署复杂度)
- 单体里一个事务能解决的事,拆开后怎么解决?(补偿 + 幂等 + 对账)
- Feign 调用为什么要幂等键?超时重试会怎样?
- 内部接口怎么保护?(不暴露 /api/inner + 服务间认证)
- 什么服务不该拆?(强一致的、频繁互相调用的——拆了反而引入分布式事务地狱)
