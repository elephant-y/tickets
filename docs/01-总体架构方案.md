# 高并发购票系统(12306 版)— 总体架构方案

> 项目定位:**求职作品**。每个技术点都要能讲清「是什么 → 怎么用 → 底层原理 → 面试怎么问」。

## 1. 核心矛盾

12306 本质上是**全球最大的秒杀系统**,所有技术选型围绕一个矛盾展开:

**单点热点库存的强一致扣减**

- **读热点**:放票瞬间,几十万人同时查询同一个车次的余票
- **写热点**:某车次+日期+座位类型只有一份库存,所有下单请求都要抢它
- **强一致性底线**:一张票绝不能卖给两个人(不能超卖)

传统方案(MySQL 直接 `UPDATE` 扣减)下,所有请求串行卡在同一行的行锁上,性能崩溃。
整个系统的设计本质是在回答一个问题:**如何让海量并发请求有序、安全地扣减一份热点库存**。
多级缓存、Redis 原子扣减、消息队列削峰,全都是这个问题的答案。

## 4. 微服务拆分

| 服务 | 职责 | 核心难点 |
|---|---|---|
| gateway | 路由、JWT 鉴权、网关层限流 | 响应式编程、Filter 链 |
| user-service | 注册、登录、用户信息 | BCrypt 加密、JWT 无状态鉴权 |
| train-service | 车次、站点、座位类型基础数据 | 基础数据变更少,读多写少,可重度缓存 |
| ticket-service | **余票查询、库存扣减、座位回流** | 系统心脏:Redis Lua 原子扣减、热点 key、不超卖 |
| order-service | **下单、订单状态机、超时取消** | 幂等、状态机、延迟消息、最终一致性 |
| pay-service | 支付、回调处理 | 幂等、验签、订单状态联动 |

## 5. 两条核心链路

### 5.1 查询链路(读,最终一致)

```
用户查余票 → gateway → ticket-service
  → 本地缓存 Caffeine(命中直接返回)
  → Redis(命中返回,回填本地缓存)
  → MySQL(兜底,回填缓存)
```
余票缓存由**库存变更时主动更新**维护,而不是过期删除(详见阶段三)。

### 5.2 下单链路(写,强一致)

```
1. 用户点「下单」→ gateway → order-service
2. 幂等校验:同一用户同一车次同一天是否已有未完成订单(唯一索引)
3. 调 ticket-service 扣库存:Redis Lua 脚本「查余票 + 扣减」原子完成
4. 扣减成功 → 创建订单(状态:待支付)→ 发 RocketMQ 延迟消息(30 分钟)
5. 支付成功 → pay-service 回调 → 订单状态:已支付 → 通知出票
6. 30 分钟未支付 → 延迟消息触发 → 取消订单 → 库存回补(座位回流)
7. 第 3 步失败 → 回补库存,保证不丢票、不超卖
```

## 6. 库存模型(核心设计决策,面试加分点)

**方案 A:余票计数模型**(入门)
库存是一个数字,`stock:{trainNo}:{date}:{seatType}`,下单时 DECR。
简单,但座位是匿名的,无法支持选座。

**方案 B:座位池模型**(进阶,12306 真实思路)
每个座位是具体资源:一趟车 1000+ 座位,用 Redis Set 存储座位 ID,下单时 `SPOP` 弹出座位并记录归属。
支持选座、候补,key 数量大但天然分片。

路线:先用 A 跑通主链路,再演进到 B,这个「演进故事」本身是面试亮点。

**热点 key 问题**:放票瞬间 `stock:G123:20261026:二等座` 是绝对热点。
解法(阶段四详讲):库存分片(拆成 10 个分片 key,随机分片扣减,分散热点)+ 本地内存余票缓存。

## 9. 开发策略:先纵后横

**原则:先用单体跑通核心业务纵切面,再横向拆分。**

1. 阶段一~四先在**单体 Spring Boot 应用**里跑通「查询 → 下单 → 扣库存 → 模拟支付」主链路;
2. 每个中间件的引入,先问「没有它会怎样?它解决什么问题?」—— 这是面试官最爱问的「为什么用」;
3. 主链路通了之后,再拆微服务、上 MQ、分库分表;
4. 第一天就 `git init`,每个阶段一个分支,求职作品必须有清晰的提交历史。

**为什么不能一上来就搭全套微服务?** 单体阶段你会亲手感受到「直接查库扛不住」「行锁冲突」的痛,
之后引入 Redis、MQ 时才有真切的动机,面试时才能讲出「我踩过什么坑、为什么这么演进」,
而不是背课文。**演进过程本身比最终架构更值钱。**
