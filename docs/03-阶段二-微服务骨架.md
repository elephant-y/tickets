## 2.1 Nacos 注册中心

### 2.1.1 为什么需要注册中心——问题与方案演进

**问题**:微服务系统中服务互相调用,调用方怎么知道被调方「在哪」(IP:端口)?
集群中实例会扩容、缩容、重启、迁移,地址是**易变信息**。

方案演进(每个方案的死穴就是下一个方案存在的理由):

1. **写死 IP:端口**:被调方重启/迁移 → 调用方全挂;扩容 → 要改所有调用方配置并重启。地址易变,代码不该持有
2. **全走 Nginx 反向代理**:只解决「外部流量入口」;服务内部 A→B 的调用不经过网关;且 upstream 列表仍要人工维护
3. **注册中心**:被调方实例启动时**主动报到**,中心维护「服务名 → 实例地址列表」;调用方按服务名查询,拿到列表自行选择

**本质**:把「服务在哪」从代码/配置中抽出来,变成一张**动态更新的映射表**。类比电话簿:你记的是名字,号码变了查电话簿,而不是把号码刻进脑子。

### 2.1.2 四大核心机制

| 机制 | 动作 | 为什么 |
|---|---|---|
| 注册 Register | 实例启动时上报 IP:端口 + 元数据(权重、分组) | 让中心知道「我上线了」 |
| 心跳 Heartbeat | 周期性续约(Nacos 默认 5s) | 证明「我还活着」,超时未跳 → 摘除 |
| 订阅 Subscribe | 调用方获取并监听实例列表变更 | 让调用方「随时知道谁在线」 |
| 下线 Deregister | 优雅停机时主动摘除 | 立即生效;否则要等心跳超时(30s)才被发现 |

**心跳周期为什么是 5 秒——两难权衡**:
- 太短(1s):网络抖动就误判下线(把活人当死人);且每实例每秒都发,中心压力线性放大
- 太长(60s):实例真挂了要 60 秒才被发现,期间调用方持续向「尸体」发请求,全部失败
- Nacos 的 5s 心跳 + 15s 判不健康 + 30s 摘除,是「故障发现延迟」与「误判率」之间的工程折中

**为什么订阅方要本地缓存副本**:若每次调用都实时问注册中心,中心就成为每次 RPC 的前置依赖——中心一挂全系统瘫痪。本地缓存让「中心不可用」时调用方仍能用最后的列表继续工作(降级),这是注册中心高可用的关键设计。

### 2.1.3 AP 与 CP:Nacos 为什么有两套协议(面试核心)

**CAP 定理**:一致性(C)、可用性(A)、分区容错性(P)三者不可兼得。网络分区必然发生(P 躲不掉),只能在 C 与 A 之间二选一。

分布式一致性协议的本质是**多数派投票**(写入要过半节点确认):
- 网络分区后,少数派节点凑不齐多数派 → 要么**拒绝写**(保 C,牺牲 A),要么**继续写**(保 A,牺牲 C)

Nacos 的两套:
- **临时实例(服务注册默认)→ AP,自研 Distro 协议**:各节点都能写、异步同步,短暂不一致可接受
- **持久实例(需显式声明)→ CP,Raft 协议**:选举 leader、多数派确认,强一致

**为什么注册数据选 AP、配置数据选 CP——通用判据(面试杀手锏)**:

> **数据不一致的代价 vs 服务不可用的代价,谁高就牺牲谁。**

- 注册数据选 AP:列表短暂过期 → 最多一次调用失败,客户端重试即可(代价小);而注册中心不可用 → 所有服务无法互相发现,系统瘫痪(代价大)→ **宁可看到过期列表,也不能让中心挂**
- 配置数据选 CP:配置错了 → 服务起不来/连错库(代价大);配置是低频操作,中心短暂不可用可接受 → **宁可短暂不可用,也不能让配置错**

同一判据还能解释:ZK 为什么是 CP(主要存元数据/配置)、Eureka 为什么是 AP(只做注册)。

### 2.1.4 Nacos 2.x 为什么把心跳从 HTTP 换成 gRPC

- 1.x:客户端每 5s 发一个 HTTP 请求做心跳——**每个心跳都是一次完整的 TCP 连接**(三次握手 + 请求响应 + 四次挥手)。实例数到几千上万时,光是心跳的连接开销就非常可观
- 2.x:gRPC 长连接(基于 HTTP/2 多路复用)——一次建连后,心跳只是长连接上的一个小请求;且双向流让服务端能**主动推送**实例列表变更,调用方秒级感知
- 这就是为什么 Nacos 2.x 要开两个端口:8848(控制台/HTTP API)+ 9848(gRPC 客户端通信)

## 2.2 Spring Cloud Gateway

### 2.2.1 为什么需要网关

每个服务都要做一批**横切关注点**:鉴权、限流、日志、跨域、协议转换。如果每个服务各做一套:
- 重复代码 N 份,改一条安全规则要改 N 个服务
- **不一致即漏洞**:有一个服务忘了加鉴权,整个系统就裸奔了

网关把这些横切逻辑**收口到一处**——它是所有请求的「安检门」。另一个动机:微服务拆多了,前端不能记住每个服务的地址,网关提供统一入口,前端只认一个域名。

### 2.2.2 为什么网关必须换 IO 模型:Tomcat 线程模型 vs Netty 事件循环(核心原理)

网关站在**所有流量的最前面**,它的并发能力就是整个系统的吞吐上限。而传统「一请求一线程」模型在万级并发下会崩。

**BIO(阻塞 IO)—— 一个连接一个线程(Tomcat 传统模型)**:
- 线程等待网络数据时**阻塞**:占着线程,什么都不干
- 线程是昂贵资源:① 每个线程约 1MB 栈内存,1 万并发 = 10GB 内存先爆;② **上下文切换**:CPU 在万级线程间切换,每次切换保存/恢复寄存器 + 冲掉 CPU 缓存(L1/L2),切换越多有效计算越少,最终 CPU 大部分时间在「切换」而不是「干活」
- 类比:一个服务员只服务一桌,上菜后站在旁边干等客人吃完。1000 桌 = 1000 个服务员,工资和场地先破产

**NIO + 多路复用 —— 一个线程管理万级连接(Netty 模型)**:
- 核心思想:不用「等待」,用「通知」。线程不阻塞在某个连接上,而是问内核:「哪些连接有数据到了?」
- Linux 的 **epoll**:把海量连接的 fd 注册进去,一个线程调一次 `epoll_wait()`,一次性拿到所有「就绪」连接的列表,逐个处理,处理完继续等
- 本质:**把等待的活交给操作系统,线程只处理有活干的连接**
- 类比:叫号系统——客人按铃,服务员扫一眼哪桌铃响就去哪桌,一个人服务 1000 桌

**为什么网关恰好是 NIO 的主场**:网关的负载特征是「**连接多、单个请求小、大量时间在等待**」(转发请求等后端响应)——线程不阻塞在等后端上,同一时间能服务成千上万个在途请求。这正是事件驱动模型最擅长的场景。

**诚实的边界(面试加分)**:NIO 不是万能的。如果每个请求都要做 CPU 密集计算(没有等待),NIO 和 BIO 吞吐没区别,反而多了事件模型的复杂度。**NIO 赢在「IO 密集、等待多」**——网关恰好是,所以网关用 Netty;业务服务计算多,继续用 Tomcat。什么场景用什么模型,而不是无脑追新。

### 2.2.3 路由三要素:Route = Predicate + Filter

- **Predicate(断言)**:请求来了,匹配哪条路由?按 Path / Header / Query 等条件
- **Filter(过滤器)**:匹配后做什么?加请求头、鉴权、限流、改写路径
- 类比:Predicate 是快递分拣规则(这个包裹走哪条线),Filter 是转运站的处理(贴签、安检、改地址)

### 2.2.6 技术栈分层(面试常问「Gateway 的技术栈是什么」)

```
┌─ Spring Cloud Gateway ── 路由框架:Route / Predicate / Filter 抽象
├─ WebFlux + Reactor ────── 响应式编程模型:Mono/Flux、背压
├─ Reactor Netty ────────── 网络引擎:EventLoop 事件循环、Pipeline 责任链
└─ 操作系统 epoll ───────── IO 多路复用
     外围:Spring Cloud LoadBalancer(lb:// 客户端负载均衡)+ Nacos Discovery(实例列表)
```

各层「为什么存在」:

1. **Netty**:封装 Java NIO(原生 Selector API 极难用),提供 EventLoop(一个线程循环处理就绪事件)与 Pipeline(每连接一条责任链,入站/出站事件依次过 Handler——与网关的 Filter 链天然同构)
2. **Reactor**:**事件循环线程不能阻塞**——Netty 线程一旦做阻塞 IO(同步等后端),整个循环卡死,该线程上的所有连接全部瘫痪。响应式把「等待」变成「订阅」:发起异步请求返回 Mono,响应到达自动触发后续处理,线程立刻腾出来服务别的连接。背压(backpressure):下游处理不过来时向上游「少给点」,防慢消费者被内存积压打爆
3. **WebFlux**:Spring 的响应式 Web 栈,与 MVC 平级互斥。Gateway 构建于其上——所以引入 `spring-boot-starter-web` 会直接冲突
4. **Spring Cloud Gateway**:Route = Predicate + Filter;内置 Path/Header/Cookie 等断言工厂、StripPrefix/AddRequestHeader/RateLimiter 等过滤器工厂;还有 **GlobalFilter**(所有路由都过,JWT 鉴权就写在这里)。处理流程:DispatcherHandler → RoutePredicateHandlerMapping(找路由)→ FilteringWebHandler(执行过滤链)→ 转发
5. **LoadBalancer + Nacos**:`lb://服务名` → 通过 DiscoveryClient 问 Nacos 拿实例列表 → 按策略(轮询/随机)选一个。这是**客户端负载均衡**(调用方自己选),对比 Nginx 的**服务端负载均衡**(Nginx 替调用方选)

对比记忆:Zuul 1.x 是上一代网关,基于 Servlet/BIO 线程模型,被淘汰的原因正是 2.2.2 讲的线程瓶颈;Zuul 2.x 与 Gateway 定位重叠,Spring 官方主推 Gateway。

## 2.3 JWT 鉴权

### 2.3.1 为什么不用 Session——分布式对「服务无状态」的硬要求

传统 Session 模式:登录后服务器在**内存里**存 Session(用户身份),下发 SessionId 给浏览器,之后每次请求带 Cookie,服务器查 Session 找用户。单体时代没问题,分布式环境下三大死穴:

1. **实例间不共享**:N 个服务实例,登录请求落在实例 A,Session 存在 A 内存;下次请求负载均衡到 B,B 没有这份 Session → 用户「被登出」。解决?Session 集中存 Redis——但每次请求都查 Redis,Redis 变成每次请求的前置依赖,一挂全线瘫痪,而且服务依然有状态
2. **内存膨胀**:Session 留在服务器内存,用户规模上来内存先爆
3. **跨端受限**:Cookie 受浏览器同源策略约束,App/小程序没有 Cookie

**根本矛盾**:Session 把「用户状态」存在服务器 = 服务有状态,违背分布式第一原则「**服务无状态**」——只有无状态,才能随意扩缩容、请求随便落到哪台实例都能处理。

### 2.3.2 JWT 的思路:把状态放回客户端

登录成功后,服务器把用户信息签名打包成一个 Token 发给客户端;之后每次请求客户端带上 Token,服务器**验证签名**就能确认「这确实是我签发的、内容没被篡改」——**不需要查任何存储**。

本质对比:**查存储(集中、有状态)vs 验签计算(本地、无状态)**。类比:Session 是存根联(服务器记着你),JWT 是介绍信(盖章的纸,谁看都认)。

### 2.3.3 结构与签名原理

```
Header.Payload.Signature   (三段 Base64URL 编码,点号分隔)

Header:    {"alg":"HS256"}                      声明签名算法
Payload:   {"uid":1,"username":"zhangsan","exp":1750000000}  声明(claims)
Signature: HMAC-SHA256(Header + Payload, 密钥)
```

- **为什么签名能防篡改**:任何人改 Payload 一个字符,重新算出的签名与原签名对不上——因为 HMAC 依赖密钥,密钥只有服务器有。验签 = 服务器用同样密钥重算一遍,比对是否一致
- **JWT 只签名,不加密**:Payload 是 Base64 编码,任何人可解码**看**内容——所以**不能放敏感信息**(身份证、密码)。JWT 保证的是「不可篡改」,不是「不可见」
- **为什么必须有过期时间 exp**:Token 签发后在过期前**无法主动吊销**(无状态的代价!)——被偷的 Token 能用到底。所以过期要短(如 2 小时),配合刷新机制;「JWT 怎么注销用户」的标准答案 = 短过期 + 黑名单(Redis)+ 刷新 token
- HS256(对称密钥,签验同一把)vs RS256(非对称:私钥签、公钥验)——微服务多服务验签场景 RS256 更优(验签方无需持有私钥),本项目先用 HS256 学习

### 2.3.4 鉴权放在网关哪一层

- 写在网关的 **GlobalFilter**(所有路由都过):从 `Authorization` 头取 Token → 验签 → 解析 uid → 放行或 401
- 为什么在网关:横切关注点收口(2.2.1),业务服务不重复写鉴权
- **透传**:网关把解析出的用户信息放进请求头(如 `X-User-Id`)传给下游,业务服务直接取用
- **白名单**:注册、登录接口必须豁免鉴权——否则「登录也要 Token」,死循环

### 2.3.5 任务清单(2.2 + 2.3 合并,网关目录已建)

1. **ticket-gateway**(空目录):pom 三依赖(gateway + nacos-discovery + loadbalancer,**禁 web starter**)、启动类、application.yml(8081,`Path=/api/**` → `lb://ticket-server`)
2. **ticket-server**:
   - 引入 `mybatis-plus-spring-boot3-starter`(Boot 3 专用 artifact)+ `mysql-connector-j`(版本由 Boot BOM 管理);数据源连本地 MySQL(**端口 3307**——你的容器映射是 3307→3306)
   - 注册接口 `POST /api/user/register`:BCrypt 加密存库(引 `spring-security-crypto`,只取加密算法,不引整包 Security)
   - 登录接口 `POST /api/user/login`:查库校验密码 → 签发 JWT(引 `jjwt` 0.12.x)
   - 受保护接口 `GET /api/user/me`:从网关透传头读用户信息并返回
3. **ticket-gateway**:JWT GlobalFilter + 白名单(register/login)
4. 坑位预警:
   - **jjwt 0.12.x 的 API 和网上大部分教程(0.9/0.11)完全不同**,以官方文档为准,别照抄旧教程
   - Gateway 是 WebFlux 环境,GlobalFilter 是**响应式写法**(实现 `GlobalFilter` 接口,返回 `Mono<Void>`,用 `chain.filter(exchange)` 放行),与 MVC 的 Filter 写法不同
   - 验签失败返回 401 也要用响应式方式写响应体(`exchange.getResponse().writeWith(...)`)

### 2.3.6 接口契约与依赖清单

**接口契约**:
- `POST /api/user/register` body `{username, password}` → 201;用户名重复 → 409
- `POST /api/user/login` body `{username, password}` → 200 `{token, expiresIn}`;密码错 → 401
- `GET /api/user/me`(需 `Authorization: Bearer <token>` 头)→ 200 `{id, username}`

**JWT 内容**:claims = uid + username + iat + exp(2 小时);HS256;密钥放 yml 自定义属性 `ticket.jwt.secret`(**≥32 字节**),ticket-server 与 ticket-gateway **同值**(否则验签必 401)

**依赖清单**:
- ticket-server 新增:`mybatis-plus-spring-boot3-starter`(3.5.5,Boot3 专用 artifact)、`mysql-connector-j`、`spring-security-crypto`(只取 BCrypt,不引整包 Security)、`jjwt` 0.12.5(api + impl + jackson)
- ticket-gateway 新增:`jjwt` 0.12.5(验签)

**数据流**:
```
register/login ──白名单放行──> ticket-server:BCrypt 校验、签发 token
其他请求 ──> 网关 JwtAuthGlobalFilter:取头、验签 ──> 透传 X-User-Id ──> ticket-server /api/user/me 读头返回
```

**ticket-server 实现清单**:User 实体(`@TableName("user")`)+ UserMapper(BaseMapper)、Register/Login 请求与响应 DTO、JwtUtil(createToken / parseToken)、UserService(register:BCrypt 加密 + 唯一键冲突处理;login:matches 校验)、UserController 三接口、`@RestControllerAdvice` 全局异常(异常→401/409 翻译,加分项)

**ticket-gateway 实现清单**:`JwtAuthGlobalFilter`(实现 `GlobalFilter, Ordered`,order 取 -100):白名单(register/login)→ 取 `Authorization: Bearer xxx` → 验签 → 失败 401(响应式写 JSON)→ 成功把 uid 写入 `X-User-Id` 头透传,`chain.filter(mutatedExchange)`

### 2.3.7 验收标准

1. `curl -X POST 8081/api/user/register` 注册成功(查库确认密码是 BCrypt 密文)
2. `curl -X POST 8081/api/user/login` 拿到 token
3. 带 token 访问 `8081/api/user/me` → 200 返回用户信息
4. **不带 token → 401;把 token 改一个字符再访问 → 401**(亲手篡改 Payload,看签名怎么拦住你——这个实验比读十遍原理都管用)
5. 直连 8080(绕过网关)访问 `/api/user/me` → 正常返回(说明鉴权收口在网关,业务服务不自带鉴权)
