# 阶段一:需求建模与数据库设计

> 目标:明确功能范围,设计全部表结构与索引,手写雪花算法 ID 生成器。
> 本阶段面试考点:① 区间余票为什么不能实时算 ② 为什么用雪花 ID 不用自增/UUID ③ 时钟回拨怎么办。

## 1. 功能范围

- 用户:注册、登录(JWT,阶段二实现,本阶段先建表)
- 车次查询:出发站 + 到达站 + 日期 → 车次列表(直达;换乘为可选扩展)
- 余票查询:某车次某日期各座位类型的区间余票
- 下单:1~5 张票(多个乘车人),占座 → 生成订单(待支付)
- 支付:模拟支付/支付宝沙箱(阶段七)
- 订单:我的订单、取消、30 分钟超时自动取消、退票(可选)
- 出票:支付成功后分配座位号

## 2. 核心设计难点:区间余票

### 2.1 为什么余票不能实时算——读写路径不对称

直观例子:G123 北京南 → 上海虹桥,经停济南西、南京南,100 个座位。

- 卖出一张 北京南→济南西,该座位在 济南西→上海虹桥 段仍可卖(席位复用)
- 此时 北京南→上海虹桥 的余票也要 -1(座位被部分占用,无法全程使用)

如果余票 = 「总数 - 实时 COUNT 订单表」,每次查询都要扫描票/订单数据(磁盘 IO),并对上千个已售区间逐一做重叠判断(CPU),而查询频率是售票频率的 1~2 个数量级——**查询成本随已售数据增长,且由最高频的操作承担**(读放大)。

**设计**:把计算成本从「查询时」挪到「售票时」——卖票是低频事件,写的时候联动更新所有重叠区间的计数(一趟车几十个区间),查询退化为读一行。

**本质**:事件驱动的增量更新(写时算)替代查询时全量计算(读时算)。通用优化原则:**把成本放在低频路径,让高频路径 O(1)**。

**代价**:写入逻辑复杂(要正确联动所有重叠区间);产生「缓存数据与事实不一致」的风险,需要补偿机制(阶段六解决)。

### 2.2 区间重叠联动规则(关键)

> 卖出区间 [i, j] 的票 → 所有与 [i, j] 有重叠的区间 [x, y] 的已售票数 +1(重叠判定:x ≤ j 且 y ≥ i)

例:线路 1-2-3 三个站(区间:1→2、2→3、1→3),座位 100:
- 卖 1→3:三个区间的已售都 +1
- 卖 1→2:区间 1→2 和 1→3 的已售 +1(2→3 不受影响)
- 卖 2→3:区间 2→3 和 1→3 的已售 +1

数据量:10 站的线路,区间数 = C(10,2) = 45,× 3 种座位类型 = **135 行/车/天**,完全可控。

### 2.3 这个模型是「保守的」——面试亮点

计数模型在席位复用场景下会**略微高估占用**(同一座位的 A→B 票和 B→C 票会重复计入 A→C 的占用),
即显示的余票 ≤ 真实余票。代价是可能少卖,收益是**绝对不超卖**。
12306 真实系统是座位级精确复用(位图),本项目阶段四用 Redis 座位池向真实模型演进。

## 3. 表结构设计

> 全部 InnoDB + utf8mb4。主键一律 BIGINT 雪花 ID。时间用 DATETIME(避免 TIMESTAMP 的 2038 问题)。

### 3.1 用户表 user

```sql
CREATE TABLE `user` (
  `id`          BIGINT       NOT NULL COMMENT '雪花ID',
  `username`    VARCHAR(32)  NOT NULL COMMENT '用户名',
  `password`    VARCHAR(64)  NOT NULL COMMENT 'BCrypt 密文',
  `phone`       VARCHAR(11)  DEFAULT NULL COMMENT '手机号',
  `id_card`     VARCHAR(18)  DEFAULT NULL COMMENT '实名证件号',
  `create_time` DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time` DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_username` (`username`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户表';
```

**为什么**:
- 密码存 BCrypt 密文,不存明文:数据库泄露 ≠ 密码泄露;且 BCrypt 自带随机盐,同样的密码两次加密结果不同,彩虹表攻击失效
- username 加唯一索引:注册时防止「先查重再插入」的竞态窗口(原理见 3.6 seat_hold)——两个并发注册同名用户,唯一索引保证只有一个成功

### 3.2 站点表 station / 车次表 train / 座位类型表 seat_type

```sql
CREATE TABLE `station` (
  `id`   BIGINT      NOT NULL,
  `name` VARCHAR(32) NOT NULL COMMENT '站名',
  `city` VARCHAR(32) DEFAULT NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_name` (`name`)
) COMMENT='站点表';

CREATE TABLE `train` (
  `id`          BIGINT      NOT NULL,
  `train_no`    VARCHAR(16) NOT NULL COMMENT '车次号,如 G123',
  `train_type`  TINYINT     NOT NULL COMMENT '1高铁 2动车 3普速',
  `start_station_id` BIGINT NOT NULL COMMENT '始发站',
  `end_station_id`   BIGINT NOT NULL COMMENT '终到站',
  `depart_time` TIME        NOT NULL COMMENT '始发时间',
  `arrive_time` TIME        NOT NULL COMMENT '终到时间',
  `status`      TINYINT     NOT NULL DEFAULT 1 COMMENT '1开行 0停运',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_train_no` (`train_no`)
) COMMENT='车次表';

CREATE TABLE `seat_type` (
  `id`         BIGINT        NOT NULL,
  `type_name`  VARCHAR(16)   NOT NULL COMMENT '二等座/一等座/商务座',
  `price_rate` DECIMAL(4,2)  NOT NULL DEFAULT 1.00 COMMENT '相对基准价倍率',
  PRIMARY KEY (`id`)
) COMMENT='座位类型表';
```

**为什么 seat_type 是独立字典表而不是枚举**:座位类型是业务数据,会增改(如新增「优选一等座」);枚举/TINYINT 写死在代码里,每次增改要发版。字典表让「类型」成为数据,由运营数据驱动,代码零改动。代价是多一次 JOIN——但类型数量个位数,缓存后成本为零。

### 3.3 车次经停表 train_station

```sql
CREATE TABLE `train_station` (
  `id`           BIGINT NOT NULL,
  `train_id`     BIGINT NOT NULL,
  `station_id`   BIGINT NOT NULL,
  `station_no`   INT    NOT NULL COMMENT '站序,从1开始',
  `arrive_time`  TIME   DEFAULT NULL COMMENT '到站时间(始发站为空)',
  `depart_time`  TIME   DEFAULT NULL COMMENT '发车时间(终到站为空)',
  `mileage`      INT    NOT NULL COMMENT '距始发站里程(公里),用于计算票价',
  PRIMARY KEY (`id`),
  KEY `idx_train_station` (`train_id`, `station_no`),
  KEY `idx_station_train` (`station_id`, `train_id`)
) COMMENT='车次经停表';
```

**为什么存 mileage(距始发站里程)而不是站间距**:区间里程 = 两站 mileage 相减,一行数据同时服务所有区间的里程计算;存站间距则区间里程 = 多行求和。**票价 = 区间里程 × 每公里基准价 × seat_type.price_rate**(真实 12306 是分段递远递减计价,本项目线性简化,面试可主动提及差异)。

### 3.4 余票表 train_seat_stock(核心)

```sql
CREATE TABLE `train_seat_stock` (
  `id`             BIGINT NOT NULL,
  `train_id`       BIGINT NOT NULL,
  `train_date`     DATE   NOT NULL COMMENT '开行日期',
  `seat_type_id`   BIGINT NOT NULL,
  `from_station_no` INT   NOT NULL COMMENT '起始站序',
  `to_station_no`   INT   NOT NULL COMMENT '到达站序',
  `total_seat`     INT    NOT NULL COMMENT '该区间票额(简化为总座位数)',
  `sold_seat`      INT    NOT NULL DEFAULT 0 COMMENT '已售(占用该区间的票数)',
  `version`        INT    NOT NULL DEFAULT 0 COMMENT '乐观锁版本号(DB兜底扣减用)',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_stock` (`train_id`, `train_date`, `seat_type_id`, `from_station_no`, `to_station_no`)
) COMMENT='车次每日区间余票表';
```

**为什么区间用站序(station_no)而不是 station_id**:
- 系统的核心判定是「区间重叠」(`x ≤ j && y ≥ i`),这要求「站」在线路上**有序可比**
- 全局 station_id 是稀疏无序的 BIGINT,「谁在前谁在后」不在 id 里,每次判定都要 JOIN 经停表拿站序
- 站序 1..n 是车次内稠密有序整数,先后关系编码在数值里,**重叠判定退化为纯整数比较,O(1) 完成,零 JOIN**
- 本质:数据结构的选择服务于最高频算法的复杂度。代价:站序跨车次无意义(表里保留 train_id);调图改站时站序会重排(本项目数据固定,不处理)

**为什么 total_seat 和 sold_seat 分两列,不直接存余票数**:
- total 是「配置」,sold 是「事实」,变更来源与频率不同——total 由运营调整(换车型、票额分配),sold 由售票/退票流水驱动
- 混存一列,配置调整会污染流水事实,出了问题无法对账;sold 作为累计售票数可与订单表独立核对
- 本质:配置与状态分离。代价:无,两列而已

**为什么加 version 乐观锁**:DB 层的并发写保护(原理见 4.3)。Redis 扣减是阶段四的主路径,DB 的 version 是兜底持久化与防乱序覆盖。

#### 3.4.1 字段逐一说明(为什么这么定)

| 字段 | 含义 | 为什么这么定 |
|---|---|---|
| id | 行主键(雪花) | 为什么不用五列联合主键:二级索引的叶子都携带主键值作为行指针,主键每宽一字节,所有二级索引树同步变胖;且雪花 id 趋势递增,每天批量生成新库存时插入有序(顺序追加最后一页)。id 对业务无意义,所以另建 uk_stock 表达业务唯一性——**主键服务物理存储,唯一键服务业务规则** |
| train_id | 车次 | 这行库存属于哪趟车。为什么不同时冗余 train_no:余票表是内部表,不对用户展示(展示由服务层缓存处理);且这是数据量最大的表,每列都要精打细算 |
| train_date | 开行日期 | 为什么「车次+日期」是两个字段而非一个「发车时刻」:业务永远按「某车次某日期」查询,两列能直接命中索引前缀;库存按天生成/过期,日期独立才能批量管理生命周期 |
| seat_type_id | 座位类型 | 同一趟车二等座与一等座是两份独立库存,互不影响 |
| from_station_no / to_station_no | 区间(站序) | 为什么 INT 而非 BIGINT:站序范围 1~几十。索引列越小,每页能装的条目越多 → 树越矮 → IO 越少(机制见 4.1) |
| total_seat | 区间票额(配置) | 为什么没有 DEFAULT:票额必须显式配置,不存在自然默认值,给默认值会掩盖初始化漏配的 bug。本项目简化为 = 该车该座位类型总座位数 |
| sold_seat | 已售计数(事实) | DEFAULT 0:新一天尚未售票,0 是自然初始态。**余票 = total - sold 是派生值,不落库**——落库就是可变的冗余,每次都要和 sold 同步,同步失败即不一致 |
| version | 乐观锁版本号 | DB 兜底扣减时防丢写(原理见 4.3) |

#### 3.4.2 uk_stock 为什么是这五列、这个顺序

1. **为什么是联合唯一索引**:业务不变量是「五元组唯一」(同一天同一区间只能有一行库存)。唯一索引把这个不变量交给数据库强制——初始化脚本有 bug 生成重复行,插入直接报错,而不是静默产生脏数据。五个单列唯一索引表达不了「五元组不重复」,还白养四棵索引树
2. **为什么列顺序是 train_id → train_date → seat_type_id → from → to**:列顺序 = 过滤粒度从粗到细。train_id 把候选从全表缩到「一趟车的全部区间」(百级行),train_date 缩到某一天,seat_type_id 缩到某座位类型(几十行),from/to 精确定位一行。B+ 树按列顺序做字典序比较,顺序决定「前缀等值能下探到树的哪一层」
3. **顺序的机械意义**:前四列等值后,候选行在叶子层物理连续(同一页或相邻几页),from/to 在连续段内仍有序,可继续二分——这是「最左前缀」在这个索引上的具体体现(原理见 4.2)

### 3.5 订单表 orders / 订单明细 order_item

```sql
CREATE TABLE `orders` (
  `id`           BIGINT       NOT NULL,
  `order_no`     VARCHAR(32)  NOT NULL COMMENT '业务订单号(展示给用户)',
  `user_id`      BIGINT       NOT NULL,
  `train_id`     BIGINT       NOT NULL,
  `train_no`     VARCHAR(16)  NOT NULL COMMENT '冗余车次号,列表展示免JOIN',
  `train_date`   DATE         NOT NULL,
  `from_station_id` BIGINT    NOT NULL,
  `to_station_id`   BIGINT    NOT NULL,
  `seat_type_id` BIGINT       NOT NULL,
  `ticket_count` INT          NOT NULL COMMENT '票数 1~5',
  `total_amount` DECIMAL(10,2) NOT NULL COMMENT '金额',
  `status`       TINYINT      NOT NULL COMMENT '10待支付 20已支付 30已出票 40已取消 50已退票',
  `pay_time`     DATETIME     DEFAULT NULL,
  `cancel_time`  DATETIME     DEFAULT NULL,
  `create_time`  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time`  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_order_no` (`order_no`),
  KEY `idx_user_status` (`user_id`, `status`, `create_time`),
  KEY `idx_train_date` (`train_id`, `train_date`, `status`)
) COMMENT='订单表';

CREATE TABLE `order_item` (
  `id`             BIGINT      NOT NULL,
  `order_id`       BIGINT      NOT NULL,
  `passenger_name` VARCHAR(32) NOT NULL COMMENT '乘车人姓名',
  `id_card`        VARCHAR(18) NOT NULL COMMENT '乘车人证件号',
  `seat_no`        VARCHAR(8)  DEFAULT NULL COMMENT '座位号,出票后回填',
  PRIMARY KEY (`id`),
  KEY `idx_order` (`order_id`)
) COMMENT='订单明细-乘车人';
```

订单状态机:

```
创建 ─→ 待支付(10) ──支付成功──→ 已支付(20) ──出票──→ 已出票(30)
              │                        │
              ├─ 30分钟超时 ─→ 已取消(40)[回补库存]
              └─ 用户主动取消 → 已取消(40)[回补库存]
                                    └──退票──→ 已退票(50)[回补库存]
```

**为什么金额用 DECIMAL 不用 float/double**:
- 浮点是二进制表示,十进制小数 0.1 在二进制中是无限循环小数(如同 1/3 在十进制中),存储即截断,累加放大误差
- 金融系统必须精确到分,DECIMAL 是定点数(十进制精确表示)。Java 层对应用 BigDecimal,禁止 float/double 参与金额运算

**为什么冗余 train_no(违反 3NF 的反规范化)**:
- 规范化(3NF)原则说不该冗余,应该 JOIN train 表拿车次号
- 但订单列表是高频读场景,每次 JOIN 都是纯开销;train_no 是车次的自然键,几乎不变
- 权衡:冗余的代价是写入时多写一列(低频、便宜),收益是读路径免 JOIN(高频、昂贵)——又是读写不对称
- 为什么站名不冗余?订单详情不是高频路径,且站名可能变更——**反规范化只用在「高频读 + 字段稳定」的地方,是有原则的取舍**

**为什么 orders 和 order_item 拆两张表**:
- 一张订单买 1~5 张票,乘客信息是「可变的数量」而非「固定属性」。宽表塞 5 组乘客字段 → 列稀疏(买 1 张空 12 列)、硬编码上限、按证件查票要写 5 个 OR
- 1:N 拆表后:乘客数自由、按证件查票是行级查询、出票回填座位是单行 UPDATE
- 本质:一对多关系必须拆表,用列表达数量是建模错误

### 3.6 占座凭证表 seat_hold(防重复购票,关键设计)

```sql
CREATE TABLE `seat_hold` (
  `id`         BIGINT      NOT NULL,
  `order_id`   BIGINT      NOT NULL,
  `id_card`    VARCHAR(18) NOT NULL COMMENT '乘车人证件号',
  `train_id`   BIGINT      NOT NULL,
  `train_date` DATE        NOT NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_hold` (`id_card`, `train_id`, `train_date`)
) COMMENT='占座凭证:同一乘车人同一车次同一天仅一张,取消/退票时删除该行';
```

**为什么需要这张表——三层因果**:

1. **「先查再插」有竞态窗口**:SELECT 判重再 INSERT,两个并发请求都查到「没买过」→ 都插入成功 → 重复购票。判重与插入之间不是原子的
2. **唯一索引的冲突检测是原子的**:两个事务并发插入相同键值,InnoDB 通过索引记录上的锁保证只有一个成功——这是**数据库白送的 CAS**,不需要应用层加锁
3. **唯一索引看的是「行存在性」,业务规则看的是「有效性」**:订单历史必须保留(取消/退票后 order_item 行还在),若把唯一键加在订单表上,行还在 = 冲突还在 = 用户永远无法重买

**设计**:独立凭证表。占座插入行,取消/退票删除行——**用行的生命周期对齐业务状态的生命周期**,把「有效性」翻译成「行存在性」,从而复用唯一索引的原子冲突检测。

**代价**:占座与释放必须成对(同一事务),释放动作一旦丢失(阶段六超时取消的消息消费失败),用户被「卡住」——所以取消流程必须可靠(消费重试 + 对账),这是阶段六的重点。

## 4. 索引设计原理

### 4.1 索引具体是怎么生效的——一次查询的完整旅程

以最高频的余票点查为例:

```sql
SELECT total_seat, sold_seat FROM train_seat_stock
WHERE train_id=1001 AND train_date='2026-10-27' AND seat_type_id=2001
  AND from_station_no=1 AND to_station_no=5;
```

**没有 uk_stock 会怎样**:全表扫描——把整张表逐行读入内存,逐行比较五个条件。假设 1000 万行,每次查询读 1000 万行;余票查询是系统最高频操作(每秒数万次),读放大直接吃光磁盘 IO 和 CPU。**索引存在的意义:让最高频的查询 O(log n) 定位而非 O(n) 扫描。**

**B+ 树结构与树高计算**:
- 内节点条目 = (五列值, 子页号),按五列字典序排序;叶子条目 = (五列值, 主键 id),叶子间有双向链表
- 行 ~50 字节,页 16KB 装 ~300 条。1000 万行 → 叶子 ~3.3 万页;内节点每页 ~300 个指针 → 300² = 9 万 > 3.3 万 → **两层内节点 + 一层叶子 = 3 层树**

**遍历过程**:
1. 从根页开始(根页常驻 Buffer Pool)
2. 节点内二分:先比 train_id,相等比 train_date,再比 seat_type_id,再 from,再 to——这就是「列顺序」的机械含义,比较规则由索引定义决定
3. 下探到叶子,页内二分找到五列全等的条目 → 拿主键 id
4. **回表**:叶子条目里没有 total_seat/sold_seat(只有五列+主键),拿 id 再去主键聚簇索引走一遍,取整行
5. 全程 3+3 层,根页常驻 → 实际 ~4 次页访问

**为什么不做覆盖索引**(把 total_seat/sold_seat 加进 uk_stock 末尾,省掉第 4 步):代价是索引叶子每行多 8 字节 → 树变胖;且每次 sold_seat 变化,索引叶子同步改(写放大)。而阶段三会把余票查询挪到 Redis/本地缓存,MySQL 只是兜底,**回表代价不在高频路径上**。知道覆盖索引能省什么、为什么这里不用,是两层理解。

**为什么是 B+ 树而不是哈希/B 树**:
- 哈希索引等值 O(1),但打散了顺序,不支持范围与前缀。而这个表的**第二高频操作恰恰是范围扫描——卖票时的区间联动更新**:卖出 [1,5] 区间,要找所有 x≤5 且 y≥1 的区间(与 [1,5] 重叠者)逐行 +1。B+ 树前缀定位到「这趟车这天这个座位类型」的连续叶子段,顺叶子链表扫出 from≤5 的行(几十行)再过滤 to≥1。哈希索引做不了
- B 树数据存在所有节点(含内节点),同样的页能装的指针少 → 树更高、IO 更多;范围扫描要回溯父节点。B+ 树数据只在叶子(内节点纯索引,树矮),叶子链表让范围扫描顺滑——InnoDB 选 B+ 树就是为「点查+范围扫」混合负载设计的
- **唯一索引的第三重身份**:并发控制的锚点。并发 UPDATE 同一行时,InnoDB 通过索引记录上的锁串行化(或乐观锁 version 不匹配影响行数 0)。没有索引,加锁定位就退化成全表扫描

### 4.2 为什么联合索引会「最左前缀失效」

**根因——B+ 树按索引列的字典序排序**:复合索引 (user_id, status, create_time) 的排序规则是先按 user_id 排,user_id 相同按 status 排,status 相同按 create_time 排。于是:

- status 只在「同一 user_id 内」有序,全局看是乱的 → 单独查 status 用不上该索引(类比:字典按字母序排,无法快速找到所有第三个字母是 X 的词)
- 范围条件截断:user_id 等值 + status 范围时,create_time 只在 status 相同的行内有序 → 用不上

**设计**:索引列顺序 = 查询条件顺序。`idx_user_status (user_id, status, create_time)` 服务「我的订单」:user_id 过滤 → status 过滤 → create_time 排序,三字段全命中且免 filesort。
`idx_train_date (train_id, train_date, status)` 服务阶段六的超时扫描与对账(按车次日期找待支付订单)。

**本质**:索引是「按指定顺序预排序的数据结构」,能加速的只有与排序顺序一致的查找。

### 4.3 为什么扣库存用乐观锁(version)而不是悲观锁

**问题**:并发更新 sold_seat,怎么防丢写?

- **悲观锁**(SELECT ... FOR UPDATE):事务期间持有行锁,其他事务排队。代价:连接占用、等待、死锁风险(多行更新顺序不一致时互等)
- **乐观锁**:读时记 version,写时 `UPDATE ... SET version = version + 1 WHERE version = ?`,影响行数为 0 = 被并发修改,重试
- 关键判断:库存行的冲突窗口极短(读→写微秒级),**实际冲突概率低**。悲观锁无论冲不冲突都付出排队代价;乐观锁只在冲突时付出重试代价——低冲突场景乐观锁吞吐更高
- 本质:锁方案与冲突概率匹配。代价:极端热点下冲突率飙升 → 重试风暴 → 吞吐崩——所以阶段四的 Redis 原子扣减才是主路径,DB 的 version 是兜底

### 4.4 其他

- **覆盖索引**:uk_stock 五字段覆盖余票查询全部 WHERE 条件,查询不回表
- **索引不是越多越好**:每个索引都是空间开销 + 每次 INSERT/UPDATE 的维护成本(写放大)

## 5. 分布式 ID:雪花算法(本阶段原理重点)

### 5.1 为什么主键必须趋势递增——聚簇索引的物理结构

**根因——InnoDB 的数据就存在主键 B+ 树的叶子节点里**(聚簇索引,索引即数据),物理上按主键排序,页大小 16KB:

- 趋势递增:新记录总落在最后一页末尾 → 顺序追加;分裂只发生在最右页(整页分裂,前面页保持满)
- 随机 ID(UUID):新记录落在任意页中间 → 该页分裂成两个半页(**50% 填充率**),树变胖变深;更糟的是被分裂的页大概率**不在 Buffer Pool 里**(默认 128MB 的内存缓存池),要先从磁盘读入 → 随机 IO
- Buffer Pool 命中率决定数据库性能:递增插入只反复访问最后的热页,常驻内存;随机插入访问全树,缓存崩掉
- 二级索引放大:每张二级索引叶子都存主键值,UUID 字符串(36 字节)比 BIGINT(8 字节)让所有索引树都变大变深

**结论:主键有序是物理存储结构(B+ 树 + 页)决定的硬需求,不是软偏好。**

### 5.2 为什么不用自增/UUID(综述)

- **UUID**:无序(见 5.1)+ 字符串大
- **自增**:分配器是「库内局部」的——ID 由数据库在插入时分配,分库分表后各库独立计数,**全局必然重复**;单点生成器有性能瓶颈;连续 ID 暴露业务量
- **雪花**:去中心化本地生成,无网络无锁,一次位运算

### 5.3 64 位布局及「为什么这么排」

```
0 | 0000...0000 | 0000000000 | 000000000000
↑        ↑            ↑            ↑
1位符号  41位时间戳     10位机器ID    12位序列号
(恒为0) (毫秒,可用69年)(最多1024台机)(同毫秒4096个)

生成公式:id = (timestamp << 22) | (workerId << 12) | sequence
```

**为什么是「时间戳+机器ID+序列号」这个组合与顺序**:
- 5.1 的结论是主键要趋势递增,分布式环境下要做到「**全局唯一 + 全局趋势递增**」
- 时间戳放最高位:不同机器同一毫秒生成的 ID,高 41 位相同 → 即使跨机器、跨分片,ID 整体仍按时间有序,保证各分片表插入有序
- 机器 ID 在中间:区分生成者,保证不同机器不冲突
- 序列号在低位:同机同毫秒内递增,用尽等下一毫秒——保证同毫秒内有序且唯一
- 布局顺序 = 排序优先级(时间 > 机器 > 序列):**把「递增性」和「唯一性」编码进 ID 本身**,不依赖任何中心协调

### 5.4 时钟回拨的三种解法(面试必问)

问题:机器 NTP 校时把时间拨回了几毫秒,再用老时间戳 + 老序列号生成 ID 就会重复。

1. **抛异常/阻塞等待**:检测到回拨直接抛异常,或自旋等到时钟追上。实现最简单,对短回拨不友好
2. **容忍小回拨**:沿用「上次时间戳」继续,序列号在已用最大值上继续递增——时间戳字段只保证粗略有序,只要 (timestamp, workerId, sequence) 组合不重复即可;序列号溢出才等待
3. **美团 Leaf 思路**:每毫秒记录该毫秒已用的最大序列号,回拨到某毫秒时从「历史最大序列号 +1」继续,保证不重复;回拨超过阈值(如 5ms)才报错

### 5.5 面试追问预案

- 序列号 4096 用完了怎么办?→ 自旋/阻塞等下一毫秒
- 机器 ID 怎么分配?→ 配置文件指定 / 启动时向注册中心(ZK/DB)申请
- 你的实现用了哪种回拨策略?为什么?→ 建议实现「方案 2 + 超过阈值报错」的组合,并写单元测试验证

### 5.6 实现规格(测试即契约)

测试文件 `SnowflakeIdGeneratorTest`(8 个用例)锁定了接口与行为,实现必须满足:

**接口契约**(由测试引用锁定):
- 构造器 `SnowflakeIdGenerator(long workerId)`;测试还使用 `SnowflakeIdGenerator(long workerId, LongSupplier timeSource)`——时间源可注入,否则时钟回拨/序列溢出无法测试
- `public static final long EPOCH` = 1767225600000L(2026-01-01 UTC)
- `long nextId()` 生成下一个 ID;`static long extractTimestamp(long id)` 解析生成时间

**行为规则**:
1. 拼装:`id = ((timestamp - EPOCH) << 22) | (workerId << 12) | sequence`
2. workerId 不在 [0, 1023] → `IllegalArgumentException`
3. 时间戳 < EPOCH → `IllegalStateException`(机器时间配置错误)
4. 回拨 ≤ 5ms:沿用 lastTimestamp,序列号继续递增;回拨 > 5ms → `IllegalStateException`
5. 同毫秒:`sequence = (sequence + 1) & 4095`,归零则自旋等待下一毫秒;新毫秒序列号归零
6. `nextId` 必须线程安全(synchronized 或等价手段),并发用例会检验

**验收**:8 个测试全绿,缺一不可。
