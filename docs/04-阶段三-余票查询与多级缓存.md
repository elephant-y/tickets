# 阶段三:余票查询(读路径)与多级缓存

> 目标:车次查询 + 余票查询接口,多级缓存(本地 Caffeine + Redis + MySQL),防穿透/击穿/雪崩。
> 注意:本阶段只做「读」;缓存与库存的一致性(写路径联动)是阶段四的核心。

## 1. 为什么必须上缓存——读放大

- 业务特征:查询与下单的比例是 1~2 个数量级(查 100 次才买 1 张);放票瞬间,几十万人查同一趟车
- 阶段一已把「余票计算」从读路径挪到写路径(写时联动更新);但**即使一次查询只读一行**,纯量打 DB 依然扛不住:
  - 内存访问 ~纳秒,磁盘 IO ~毫秒,差 4~5 个数量级
  - MySQL 连接数有限(一连接一线程,与网关讲的线程模型同源),单机几千 QPS 到头
- 缓存的本质:**空间换时间 + 时间局部性**——刚被查过的数据大概率马上再被查(放票瞬间,百万查询集中在几百趟车上),把高频热数据放进内存,DB 只兜底

## 2. 多级缓存架构:为什么是两层

| 层 | 位置 | 速度 | 特征 |
|---|---|---|---|
| 本地缓存 Caffeine | 每个服务实例的 JVM 堆内 | 纳秒级 | 每实例一份:快,但**数据不共享、容量小** |
| Redis | 独立进程,全集群共享 | 微秒级(一次网络往返) | 共享一份:容量大,但**每次查询都要过网络** |

为什么两层都要:
- **只有 Redis**:百万 QPS 时,每次查询一个网络往返,Redis 自己成为瓶颈(单机 Redis 十万 QPS 级)
- **只有本地**:每个实例各缓存一份,内存重复;更致命的是**库存变化时无法统一失效**——实例 A 更新了余票缓存,实例 B 的本地缓存还是旧的,且没有手段通知它
- **分工**:本地缓存挡「同实例的重复查询」,Redis 挡「跨实例的重复查询」,MySQL 兜底

读路径:
```
查询 → 本地命中?→ 返回
      └ miss → Redis 命中?→ 回填本地 → 返回
              └ miss → MySQL → 回填 Redis + 本地 → 返回
```

## 3. 三大缓存问题(现象 → 根因 → 解法 → 代价)

### 3.1 穿透:查询不存在的数据

- **现象**:查询一个**不存在**的数据(如不存在的车次 id、30 天窗口外的日期),缓存永远不命中,每次查询都直达 DB
- **根因**:缓存只能存「存在的数据」,「不存在」这个事实没有存进缓存——miss 无法区分「没缓存」和「真没有」
- **为什么危险**:攻击者构造大量不存在数据的查询,绕过缓存直打 DB(与 DDoS 同构),一个接口就能把库打挂
- **解法**:
  - 空值缓存:DB 确认「不存在」后,把这个否定结果也缓存起来(短 TTL,如 1 分钟)——「不存在」也是一种数据
  - 布隆过滤器:预先把全部存在的 key 灌入位图,查询前先问「在不在」——成本高(误判率、数据增删要维护),本项目不采用
- **代价**:空值缓存占用内存存「垃圾」;且数据刚被创建时,可能短暂查到「不存在」(TTL 内的不一致)——TTL 短则影响小

### 3.2 击穿:热点 key 失效的瞬间

- **现象**:某个**热点 key**(G101 今天的余票)过期的一瞬间,海量并发请求同时 miss、同时回源 DB,且可能**同时重建缓存**(重建风暴)——DB 瞬间被打爆
- **根因**:过期 + 热点 + 并发回源。冷 key 过期时没有并发,无感;热点 key 把「并发 miss」放大成「并发打库」
- **解法**:
  - 互斥锁:重建时只允许一个请求回源,其余等待锁释放后直接读缓存——代价:请求排队(高峰时等待的请求形成队伍)、实现复杂(分布式锁,阶段四的 Redisson 会复用)
  - 逻辑过期:缓存**永不过期**,值里存「逻辑过期时间」;读取时发现已逻辑过期 → **先返回旧值**,异步线程去重建——代价:短暂数据不一致(用户可能看到几秒前的余票)
- **为什么 12306 能接受旧余票**:余票显示的语义就是「缓存时间点的快照」(12306 的查询结果带缓存时间戳)——查询本身承诺的是「大致准确」,下单时的强校验(阶段四)兜底
- **我们的选择**:逻辑过期方案——不阻塞用户、无锁、和「余票允许秒级延迟」的业务语义契合;代价(短暂旧数据)由阶段四的「下单时 Redis 原子校验」兜底

### 3.3 雪崩:大面积 key 同时失效

- **现象**:大量 key 在同一时刻过期(同样的 TTL、同一批写入),失效瞬间全部流量砸向 DB
- **根因**:过期时间的「同时性」——TTL 一致,失效时刻就集中
- **解法**:TTL 加随机扰动(如 × [0.9, 1.1])——失效时刻打散。代价:无
- **延伸**:Redis 本身宕机 = 所有缓存整体失效(更严重的雪崩)→ 靠限流降级兜底(阶段九压测时展开,不是本阶段任务)

## 4. 余票缓存的特殊难点(阶段四预告)

- 普通数据(用户信息)几乎不变,TTL 过期策略足够
- **余票每卖一张就变**:缓存显示「有票」,库存实际扣光 → 用户下单才知道没票
- 所以余票缓存**不能只靠 TTL**:阶段四扣库存时**主动更新/删除**余票缓存;阶段三先用短 TTL(如 30 秒)占位
- 面试对比记忆:普通缓存 = 过期驱动;余票缓存 = 变更驱动(写路径通知)

## 5. 任务清单

1. **环境**:Docker 起 Redis(`docker run -d --name redis -p 6379:6379 redis:7`)
2. **依赖**:`spring-boot-starter-data-redis` + `com.github.ben-manes.caffeine:caffeine`
3. **配置**:yml 加 redis 连接 + 缓存参数(本地容量、TTL 区间)
4. **实体/Mapper**:Train、TrainStation(阶段一只建了表,实体还没写)
5. **接口**:
   - `GET /api/train/search?from=&to=` —— 查「两站都停靠」的车次。核心 SQL 是**经停表自连接取交集**:
     ```sql
     SELECT t.* FROM train t
     JOIN train_station a ON a.train_id = t.id AND a.station_id = :from
     JOIN train_station b ON b.train_id = t.id AND b.station_id = :to
     WHERE a.station_no < b.station_no
     ```
   - `GET /api/ticket/stock?trainId=&date=` —— 读 train_seat_stock 余票
6. **多级缓存**:三级读路径 + 回填;空值缓存(防穿透);随机 TTL(防雪崩);逻辑过期(防击穿)
7. **验证**:日志打印命中层级(本地/Redis/DB),连续查两次第二次命中本地;清 Redis 后第三次走 Redis
