# 阶段八:分库分表

> 目标:orders/order_item 按 user_id 分 4 个逻辑库,学习分片键选择、绑定表、全局 ID 的意义。
> 核心命题:**数据量大到单库装不下时,怎么把「一张表」拆成「四张表」而业务代码几乎不改**。

## 1. 为什么分(以及为什么「不轻易分」)

- **分的动机**:单表行数爆炸(亿级)→ B+ 树变深、单库写入瓶颈、备份/恢复变慢
- **分的代价**:跨片 JOIN 失效、分布式事务、**唯一索引失效**(uk 只能保证片内唯一!)、运维复杂度翻倍
- 本项目现在数据量几千行,分库分表是**预演**——面试正确姿势:「我知道什么体量才需要分,以及分的代价是什么」

## 2. 核心概念

### 2.1 分片键(Sharding Key):一行数据去哪个片的依据

选择标准:① **高频查询的过滤条件**(查询能路由到单片,不广播)② **分布均匀**(不倾斜)。

orders 选 **user_id**:「我的订单」是最高频查询,按 user_id 直接路由到一片;用户天然均匀。

### 2.2 绑定表(Binding Tables):关联表必须「同键同片」

orders : order_item = 1 : N。如果 orders 按 user_id 分、order_item 按 order_id 分,查「订单+明细」时明细要**广播到所有片**——关联 JOIN 直接废掉。

解法:order_item 也按 **user_id** 分片(与 orders 同键同算法),同一个订单的主单和明细**必然落在同一片**,JOIN 不跨片。ShardingSphere 的「绑定表」配置就是声明这个关系。

**代价:order_item 必须冗余 user_id 列**(它原本没有!)——分片键必须存在于表里,这是分库分表最常见的「表结构改造」。

### 2.3 全局 ID:阶段一伏笔第三次兑现

分片后每个片不能各自自增(跨片冲突)。雪花 ID **全局唯一、不依赖数据库**——阶段一手写的雪花在分片场景下价值最大化:主键天生跨片唯一,不需要任何额外协调。

### 2.4 广播表(概念,本项目不落地)

station/seat_type 这种「每个片都查」的小表,可以每个片放一份(只读共享)。本项目这些表不分片(留在主库),概念面试要会讲。

## 3. 落地设计(本地模拟)

- 同一个 MySQL 实例建 **4 个逻辑库**:ticket_0 ~ ticket_3(真分库 = 不同实例,本地多 schema 是教学标准姿势)
- 每个分片库只放 **orders + order_item** 两张表(order_item 含 user_id);其余表留在主库 ticket
- 分片规则:`user_id % 4` → 路由到 ticket_{0..3}
- ShardingSphere 对「未配置分片规则的表」走默认数据源(ticket)——**部分表分片**,业务代码几乎无感

## 4. 任务清单

1. **建 4 个分片库**:ticket_0 ~ ticket_3,各建 orders/order_item(order_item 加 user_id 列)
2. **依赖**:`org.apache.shardingsphere:shardingsphere-jdbc-core-spring-boot-starter:5.4.1`(Boot 3 兼容版)
3. **yml 配置**:数据源(ticket + ticket_0~3)+ 分片规则(orders/order_item:user_id % 4,绑定表)
4. **代码改造**:OrderItem 实体加 userId 字段;saveOrderAndItems 插明细时 setUserId(下单时 req 里有 userId)
5. **验收**:
   - 4 个不同 userId 下单 → 订单分别落在 ticket_0~3(数据分布验证)
   - 同一用户的订单全部在同一片
   - 「我的订单」查询正确路由(日志/结果验证)
   - 之前的全链路(下单/支付/取消)在分片后仍然正常——**业务代码几乎没改就完成了分片**
