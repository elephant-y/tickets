## 高并发购票系统(仿 12306 核心链路)| 个人项目 | 2026.10 – 至今

**项目描述**:面向放票瞬间"读热点 + 写热点"的高并发火车票购票系统,覆盖 查票 → 余票 → 下单 → 排队 → 支付 → 出票 全链路;先单体跑通主链路、再演进为 6 个微服务,前端 Vue3 + Element Plus 完整联调。

**技术栈**:JDK 17 / Spring Boot 3.2 / Spring Cloud Alibaba(Nacos、Gateway、OpenFeign)/ Redis 7(Lua)/ RocketMQ / ShardingSphere / MySQL 8 / Caffeine / MyBatis-Plus / JMeter / Docker Compose

1. **放票瞬间热点库存并发扣减**:同一区间仅一份库存,MySQL 行锁扣减单行仅几百 QPS,区间票售出还需联动更新所有重叠区间。采用"写时联动更新"库存模型 + Redis Lua 原子扣减(先全部校验、再全部扣减),叠加 DB 乐观条件兜底与 seat_hold 唯一索引防重幂等。压测 14.6 万笔订单 **0 超卖**,并发 20 抢 10 张票精确卖出 10 张。

2. **同步下单扛不住放票洪峰**:线程池打满 → 响应变慢 → 用户重试 → 流量翻倍。将下单改为"提交即受理"的异步排队,RocketMQ 消费者按序扣库存建订单,用户轮询结果。压测入口 ≈900 TPS 对出票 ≈150 单/秒,**削峰比 6:1**,积压 5.2 万条停压后全部消化、**零丢失**。

3. **查询:下单 ≈ 100:1,放票瞬间数十万请求查同一车次**。Caffeine + Redis + MySQL 三级缓存:空值缓存防穿透、随机 TTL 防雪崩、逻辑过期防击穿,余票缓存由扣减主动失效(变更驱动)。100 并发全链路平均 RT 20ms、**0 错误**。

4. **订单量增长单库单表到瓶颈**,分片后唯一索引仅保证片内唯一、关联查询易跨片。ShardingSphere 按 user_id 分 4 片,orders/order_item 绑定表同键同片,手写雪花 ID 保证全局唯一。压测发现订单全部落在单片,定位为雪花 ID 取模落在恒为 0 的序列段,修复后四片分布 6357/4136/2966/5150,业务代码几乎零改动。

5. **下单 30 分钟未支付需自动取消并回补库存**,延迟消息可能丢失、补偿可能失败。RocketMQ 延迟消息(等级 16 = 30min)驱动超时取消,取消用 `WHERE status=10` 条件更新实现天然幂等,叠加定时对账任务形成"即时补偿 + 定时对账"双保险,支付回调三处幂等。200 个用户完整购票全部出票成功,状态迁移零异常。

6. **"高并发"需要数字证据**,压测中发现订单号高并发下撞号:生日悖论使 645 TPS 下理论碰撞 12.5 次/分钟与实测 12 次吻合。建立 JMeter 阶梯加压 + DB 数据核对方法论,订单号改为与雪花主键同源构造唯一。修复后 18,609 单 **0 撞号**,并定位出系统拐点与出票瓶颈。

## 使用说明

1. **数字口径**:压测为本机单机(客户端与后端同机),数字证明"架构成立 + 缺陷定位",不是真实容量;面试被问"900 TPS 是不是太低"时主动说明口径,反而加分(诚实)。云服务器部署(阶段十)后重跑本套脚本,可替换为真实容量数字。
2. **按 JD 裁剪**:面试普通业务岗 → 保留 1/2/5;面试高并发/中间件岗 → 全保留,重点讲 2/6。
3. **不写没实现的东西**:架构文档里的 Sentinel / Prometheus 尚未落地,简历未列,面试若被问到可答"计划中"。
