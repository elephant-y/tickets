# 阶段四:下单占座(写路径,系统心脏)

> 目标:下单主链路 —— 幂等校验 → Redis Lua 原子扣减(区间联动)→ 建订单 + 占座凭证 → 失败回补。
> 核心命题:**如何让海量并发请求有序、安全地扣减一份热点库存,且绝不超卖**。

## 1. 为什么写路径是最难的一环

阶段三的缓存解决了「读」:读可以缓存、可以容忍秒级延迟。但「写」没有缓存可加——**库存扣减必须实时、必须强一致**:

- 读热点可以多副本分担(本地/Redis),**写热点只有一个真相**:某车次某日期某区间的 sold 计数,所有下单请求都要改它
- 读可以返回旧值,**写错了就是超卖/少卖**,没有「最终一致」可商量
- 所以写路径的命题是:**把并发争抢,串行化或原子化——而且不能牺牲吞吐**

## 2. 四种扣减方案的演进(面试必问,每种方案的死穴 = 下一种存在的理由)

### 方案1:MySQL 直接 UPDATE(基线,必崩)

```sql
UPDATE train_seat_stock SET sold_seat = sold_seat + 1, version = version + 1
WHERE train_id = ? AND train_date = ? AND ... AND sold_seat < total_seat
```

- 正确性 ✓(WHERE 条件 + 行锁保证不超卖)
- **死穴**:InnoDB 行锁 —— 同一行的 UPDATE 串行化,并发请求在锁上排队。热点行(热门车次)的争抢让单行 QPS 只有几百;且排队期间每个事务占着一个数据库连接,连接池被拖垮,波及全库
- 根因:数据库的强项是事务和持久化,**弱项是热点行的并发写**——用错工具

### 方案2:Redis DECR(快了,但不安全)

```bash
DECR stock:G101:20261028:二等座:1:4
```

- Redis 单线程执行命令,DECR 原子,单实例 10 万 QPS
- **死穴**:「扣」是原子的,但「**判断余票够不够 → 扣**」不是。DECR 不判断,扣到负数照样返回——超卖。先 GET 再 DECR?两步之间有竞态窗口:两个并发请求都 GET 到 1,都 DECR,库存变 -1
- 教训:**单命令原子 ≠ 业务操作原子**,「查+判+扣」必须作为一个整体原子执行

### 方案3:Redis Lua(阶段四的落地方案)

```lua
-- 扣减脚本:KEYS = 所有重叠区间的 key,ARGV = 各区间扣减数
-- 第一遍:全部检查,任何一个余票不足 → 整体失败
-- 第二遍:全部扣减
```

- **为什么 Lua 有原子性**:Redis 是单线程事件循环,一个客户端发来的 Lua 脚本**从头到尾执行完,期间不穿插任何其他命令**——脚本内部的「查→判→扣」天然不会被并发插入
- 性能:脚本是「内存内的几次 HGET/SET 级操作」,一次网络往返完成整个业务判断,依旧 10 万级 QPS
- 这正是 12306 级系统的标准扣减姿势

### 方案4:本地内存扣减 + 异步落库(12306 真实思路,了解)

- 每趟车的库存常驻**实例内存**,扣减在 JVM 内完成(纳秒级),定期/异步同步 DB
- 收益:彻底摆脱网络,百万级 QPS 也可达
- 代价:内存数据有丢失风险(实例宕机 = 已扣未落库的票丢失),需要「先落库意向、后扣内存」等复杂保障
- 本项目做到方案 3;面试讲演进到方案 4 的思路即可

## 3. 区间联动扣减(阶段一的伏笔兑现)

卖区间 [i,j] 的票,所有与 [i,j] 重叠的区间 [x,y] 的 sold 都要 +1(重叠判定:x ≤ j 且 y ≥ i)。

**Lua 里的实现**:
1. 先查出「这趟车这天这个座位类型」的所有区间余票(HGETALL 一个 hash 或扫多个 key)
2. 计算重叠集合,第一遍:**逐个检查余票是否充足,任何一个不足 → 返回失败**(Lua 内没有事务回滚,必须先验后扣!)
3. 第二遍:全部通过后才逐个扣减
4. 返回成功/失败码

**为什么必须「先全部验、再全部扣」**:Lua 的原子性保证脚本不被穿插,但**不提供回滚**——如果边验边扣,扣到一半发现某个区间不足,Lua 无法「撤销」已扣的部分。两遍遍历 = 用「验后扣」模拟事务。

## 4. 不超卖的三重保障(纵深防御)

| 层 | 机制 | 防什么 |
|---|---|---|
| 第一层 | Lua 脚本内「判断 ≥ 扣减数」才扣 | 正常路径的超卖 |
| 第二层 | 扣减脚本的检查条件与执行原子一体 | 并发竞态(查扣分离) |
| 第三层 | DB 兜底:UPDATE ... WHERE sold_seat + n ≤ total_seat(乐观条件)| 即使 Redis 层被绕过/数据漂移,DB 层也拒超卖 |

**为什么还要第三层**:缓存层的一切都可能丢(Redis 重启、key 过期、人工操作),DB 是最终真相——把「不超卖」也编码进 DB 的 UPDATE 条件,任何路径都超不了。

## 5. 幂等:同一用户不能重复下单(seat_hold 的第二次实战)

- 场景:网络重试、用户双击、前端超时后重发 —— 同一个下单请求可能到达两次
- 防线:阶段一的 seat_hold 表,`uk_hold(id_card, train_id, train_date)` 唯一索引
- 流程:扣减**之前**先尝试插入 seat_hold → 唯一键冲突 = 已买过 → 409 拒绝(而不是再扣一次库存!)
- **顺序很重要**:先幂等检查、后扣库存——反过来会「扣了库存却因幂等失败」,白白损失一张票
- 面试点:「先查再插」有竞态窗口,唯一索引冲突是原子的判重结果(阶段一/阶段二都讲过,现在第三次实战)

## 6. 补偿:下单失败要把票还回去(先扣后补)

主流程:幂等检查 → Lua 扣减 → 建订单 + seat_hold 落库。
若「建订单/落凭证」失败(DB 抖动),**已扣的库存必须回补**:

```lua
-- 回补脚本:与扣减镜像,所有重叠区间 sold 减回去
```

- 为什么先扣后补而不是先建订单后扣:扣减失败(没票)时什么都不用做,成本最低;建单失败概率远小于扣减失败,补偿路径短
- 回补本身也可能失败 → 引入重试/对账(阶段六的最终一致性会展开)

## 7. 扣减成功后:失效读缓存(阶段三伏笔兑现)

余票被扣了,阶段三的 stock 缓存还显示旧值 → **下单成功后主动失效**:
- 本地缓存:`local.invalidate(key)`
- Redis:`redis.delete(key)`
- 这就是「变更驱动」vs「过期驱动」:普通数据靠 TTL,余票靠写路径主动通知(阶段三 §4 预告的)

## 8. 任务清单

1. **实体/Mapper**:Order、OrderItem、SeatHold(表阶段一已建,实体还没写)
2. **Lua 脚本**(resources 下):扣减脚本(两遍遍历)+ 回补脚本
3. **StockKey 设计**:`stock:{trainId}:{date}:{seatTypeId}:{fromNo}:{toNo}` → 余票数(与 DB 的 sold/total 映射:Redis 存「剩余数」,扣减 = 减剩余)
   - 简化决策:Redis 里存**剩余票数**(total-sold),下单扣减 DECR 语义;回补 INCR。初始化:首次访问时从 DB 加载(懒加载)
4. **OrderService 主流程**:
   ```
   ① 参数校验(乘车人、日期范围、票数 1~5)
   ② 幂等:逐乘车人插入 seat_hold(唯一键冲突 → 409)
   ③ 计算重叠区间 → Redis Lua 扣减(失败 → 409 余票不足,并回滚已插的 seat_hold)
   ④ 建订单(待支付)+ 订单明细
   ⑤ 失效余票缓存(本地 + Redis)
   ⑥ 任何失败 → 回补库存 + 清理 seat_hold
   ```
5. **接口**:`POST /api/order/create`(需登录,网关注入 X-User-Id)
6. **验证**:
   - 正常下单 → 余票减少、订单待支付
   - 余票不足 → 409
   - 重复下单(同一乘车人同车次同天)→ 409
   - **并发压测**:N 线程同时抢 100 张票 → 恰好卖 100,不超卖(JMeter 或 Java 并发测试)

## 11. 已知边界(阶段五/六解决)

- Redis 库存 key 丢失且未回补时,INCRBY 会写错误初始值 → DB 兜底条件 + 阶段六对账
- 下单为同步流程,高峰无削峰 → 阶段五 RocketMQ 异步化
- 订单无超时取消 → 阶段六延迟消息 + 座位回流
