# 阶段六:订单状态机与座位回流

> 目标:30 分钟超时未支付自动取消(延迟消息)、取消/退票的座位回流链路、对账兜底。
> 核心命题:**订单的完整生命周期 + 最终一致性闭环(即时补偿 + 定时对账)**。

## 1. 订单状态机全景

```
10 待支付 ──支付成功(阶段七)──> 20 已支付 ──出票──> 30 已出票
    │                              │
    ├─ 30分钟超时(本阶段)──> 40 已取消
    ├─ 用户主动取消(本阶段)─> 40 已取消
    │
    └─(20 已支付)──退票(本阶段,可选)──> 50 已退票
```

本阶段实现三条迁移:**10→40(超时自动)、10→40(主动取消)、20→50(退票)**。

## 2. 延迟消息:30 分钟怎么「定时」

### 2.1 机制

下单成功(executeOrder 建单后)发一条**延迟消息**到 topic `ORDER_TIMEOUT`,body 只有 orderId:

```java
Message msg = new Message("ORDER_TIMEOUT", String.valueOf(orderId).getBytes());
msg.setDelayTimeLevel(16);   // 等级 16 = 30 分钟(见等级表)
producer.send(msg);
```

RocketMQ **18 个固定延迟等级**:1s 5s 10s 30s 1m 2m 3m 4m 5m 6m 7m 8m 9m 10m 20m **30m(16)** 1h 2h。

**实现原理**:延迟消息先存进 broker 内部的「延迟队列」,定时任务到点把它投进真实队列——消费者无感知,只看到「到点才来的消息」。

### 2.2 测试技巧(重要)

30 分钟没法等,把等级**配置化**:yml 里 `ticket.order.timeout-level: 5`(1 分钟)测试,生产改 16。延迟等级在 `Message.setDelayTimeLevel` 是写死的 int,从配置读。

## 3. 取消链路:下单的镜像

**消费者 OrderTimeoutConsumer**:收到 orderId → 查订单 → status=10 才取消;否则跳过(幂等,延迟消息也可能重复投递)。

**executeCancel(orderId)——和下单十步的镜像关系**:

```
事务内:
  ① 订单 10 → 40(WHERE status = 10 ← 状态机幂等:重复取消时 0 行受影响,直接返回)
  ② DB sold_seat 每重叠区间 -count(真相层回减)
  ③ 删除 seat_hold(释放凭证 → 该乘车人可以重新购买,「占座与释放成对」第三次兑现)
事务外:
  ④ Redis 库存回补(refund 脚本,下单补偿时用过的那个)
  ⑤ 失效余票缓存
```

**为什么 ① 用 WHERE status=10 做入口**:取消是状态机的「迁移」,条件更新保证只迁移一次——消息重复投递、用户同时点取消,第二次 UPDATE 影响 0 行,直接返回。**状态机条件更新 = 天然的幂等**。

## 4. 对账:最终一致性的最后一块(阶段四伏笔兑现)

即时补偿(refund 脚本 + 状态回写)可能失败:Redis 挂、消费者崩、消息丢失。所以**最终一致性 = 即时补偿 + 定时对账**:

- 定时任务(每 5~10 分钟,`@Scheduled`):
  1. 扫描「status=10 且 create_time 超过 30 分钟」的订单 → 兜底取消(防延迟消息丢失)
  2. 扫描「status=40 但 seat_hold 仍存在」→ 补删凭证
  3. (进阶)扫描「status=40 但 sold 与订单不符」→ 重算修正
- 面试金句:**主路径靠消息驱动(实时),兜底靠定时扫描(最终)——两条腿,任何一条断了另一条兜着**

## 5. 退票(可选加分)

- 入口:`POST /api/order/refund?orderId=`,校验订单属于当前用户 + status=20(已支付)
- 链路与取消完全相同:20→50 + sold 回减 + 删凭证 + Redis 回补 + 失效缓存
- 退款(钱)是阶段七支付的事——本阶段只做「票的退还」,注释里标明「退款待支付模块」

## 6. 任务清单

1. **延迟消息发送**:executeOrder 建单成功后发 ORDER_TIMEOUT 消息(delayLevel 从 yml 读)
2. **OrderTimeoutConsumer**:查订单 → status=10 → executeCancel;否则跳过
3. **executeCancel(orderId)**:① 事务:状态 10→40(条件更新)+ sold 回减 + 删凭证 ② 事务外:refund 脚本 + 失效缓存
4. **主动取消接口** `POST /api/order/cancel?orderId=`(复用 executeCancel,校验订单归属)
5. **(可选)退票接口** `POST /api/order/refund?orderId=`
6. **对账任务**:@Scheduled 定时扫描(第 4 节的三条)
7. **验收**:
   - 下单 →(delayLevel 设 1 分钟)→ 1 分钟后轮询:订单 40、DB sold 回减、凭证已删、Redis 回补、缓存失效
   - 重复取消(取消已取消的)→ 幂等,无副作用
   - 手动取消接口同链路验证
   - 对账任务:手工制造「脏数据」(把某订单改回 10)→ 定时任务兜底取消
